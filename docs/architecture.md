# Moni Architecture

이 문서는 Moni의 전체 시스템 구조, 데이터 흐름, 프론트엔드·백엔드·AI 엔진의 역할을 설명합니다.

Moni는 사용자의 소비 기록과 예산 정보를 기반으로 월말 예상 지출을 계산하고, 예산 압박도를 분석해 오늘 바로 실천할 수 있는 개인화 지출 제한형 챌린지를 제공하는 소비 습관 코칭 앱입니다.

---

## 1. 전체 구조

```text
사용자
↓
React Native / Expo Web Frontend
↓
FastAPI Backend
↓
PostgreSQL / SQLite DB
↓
AI Engine
↓
예측 결과 / 예산 압박도 / 챌린지 생성
↓
Frontend 화면 표시
```

현재 개발 및 테스트는 Expo Web 기준으로 진행합니다.

---

## 2. 구성 요소별 역할

| 영역        | 역할                                     |
| --------- | -------------------------------------- |
| Frontend  | 사용자가 소비 기록, 예산, 리포트, 챌린지를 확인하고 조작하는 화면 |
| Backend   | 인증, 사용자 정보, 지출, 예산, 리포트, 챌린지 API 제공    |
| Database  | 사용자, 거래, 카테고리 예산, 챌린지, XP/레벨 정보 저장     |
| AI Engine | 소비 데이터를 전처리하고 예상 지출, 예산 압박도, 챌린지 후보 생성 |
| Docs      | API 명세, 아키텍처, 테스트 시나리오, 프론트 실행 문서 제공   |

---

## 3. 핵심 서비스 흐름

Moni의 핵심 흐름은 다음과 같습니다.

```text
소비 기록 입력
→ 현재 소비 속도 계산
→ 월말 예상 지출 계산
→ 예산 대비 압박도 분석
→ 오늘의 지출 제한형 챌린지 생성
→ 챌린지 완료 시 XP / 레벨 반영
```

Moni는 단순히 소비 결과를 보여주는 가계부가 아니라, 소비가 발생하기 전에 오늘의 행동 목표를 제안하는 소비 코칭 앱을 목표로 합니다.

---

## 4. 주요 데이터 흐름

### 4.1 회원가입 / 로그인

```text
Frontend
→ POST /signup 또는 POST /login
→ Backend
→ 사용자 생성 또는 인증
→ access_token 반환
→ Frontend가 토큰 저장
→ 이후 API 요청에 Authorization 헤더 포함
```

인증이 필요한 API는 다음 헤더를 사용합니다.

```http
Authorization: Bearer {access_token}
```

회원가입과 로그인을 제외한 대부분의 API는 JWT 토큰을 필요로 합니다.

---

### 4.2 지출 기록 흐름

```text
사용자 지출 입력
→ Frontend 소비 탭
→ POST /transactions
→ Backend
→ DB에 거래 저장
→ Frontend가 거래 목록 재조회
→ 홈 / 소비 / 리포트 화면에 반영
```

지출 수정 시에는 다음 흐름을 따릅니다.

```text
기존 지출 선택
→ 날짜 / 금액 / 결제처 / 카테고리 수정
→ PATCH /transactions/{tx_id}
→ DB 업데이트
→ Frontend 거래 목록 재조회
```

지출 날짜는 월간 리포트 계산에 직접 영향을 줍니다.
예를 들어 `tx_date`가 지난달이면 이번 달 리포트에는 포함되지 않습니다.

---

### 4.3 예산 관리 흐름

```text
사용자 카테고리 선택
→ 월 예산 / 알림 기준 / 미션 포함 여부 수정
→ PATCH /categories/{category_id}
→ DB 업데이트
→ 소비 탭 게이지 및 리포트 예산 상태 반영
```

카테고리 예산은 월말 예상 지출을 직접 바꾸는 값이 아닙니다.
예산은 예상 지출과 비교되어 예산 압박도, 게이지, 초과/여유 상태를 결정합니다.

---

### 4.4 월간 리포트 흐름

```text
Frontend
→ GET /reports/monthly
→ Backend
→ 이번 달 거래 조회
→ 현재 지출 합계 계산
→ 월말 예상 지출 계산
→ 예산 압박도 계산
→ 요일별 소비 리듬 계산
→ 카테고리별 예산 상태 계산
→ Frontend에 응답
```

월간 리포트는 다음 정보를 포함합니다.

| 항목          | 설명                           |
| ----------- | ---------------------------- |
| 현재 지출       | 이번 달 현재까지 기록된 총 지출           |
| 월말 예상 지출    | 현재 소비 속도 기반 예상 월말 지출         |
| 예산 압박도      | 월말 예상 지출 / 월 예산              |
| 요일별 소비 리듬   | 요일별 소비 합계                    |
| 카테고리별 예산 상태 | 카테고리별 현재 지출, 예상 지출, 예산 대비 상태 |

---

### 4.5 챌린지 생성 흐름

```text
Frontend
→ GET /challenges/today
→ 오늘 챌린지 존재 여부 확인
→ 없으면 POST /challenges/generate
→ Backend
→ AI Engine 호출
→ 예측 결과 / 예산 압박도 기반 챌린지 생성
→ DB 저장
→ Frontend 표시
```

챌린지 완료 흐름은 다음과 같습니다.

```text
사용자 챌린지 완료
→ PATCH /challenges/{challenge_id}/status
→ status: SUCCESS
→ XP 증가
→ 레벨 반영
→ Frontend 화면 업데이트
```

완료 취소 흐름은 다음과 같습니다.

```text
사용자 완료 취소
→ PATCH /challenges/{challenge_id}/status
→ status: PENDING
→ XP 재반영
→ Frontend 화면 업데이트
```

## 5. 월간 리포트 월말 예상 지출 계산 기준

월말 예상 지출은 예산 기준이 아니라 실제 지출 속도 기준으로 계산합니다.

```text
월말 예상 지출 = 이번 달 현재 지출 ÷ 오늘 날짜 × 이번 달 전체 일수
```

예를 들어 6월 10일까지 100,000원을 사용했다면 다음과 같이 계산합니다.

```text
100,000 ÷ 10 × 30 = 300,000
```

따라서 예산을 수정해도 월말 예상 지출 자체는 바로 바뀌지 않습니다.

예산 수정으로 바뀌는 값은 다음과 같습니다.

* 예산 압박도
* 예산 게이지
* 초과 예상 / 여유 예상
* 챌린지 생성 기준

> 위 선형 추정은 리포트 화면 전용입니다.
> 챌린지 엔진(`prediction.py`)은 이와 별도로,
> 이미 쓴 금액은 실제값으로 두고 남은 기간만 카테고리별 Prophet(또는 simple-average)로
> 예측해 합산하므로, 두 화면의 예상치는 다를 수 있습니다.

---

## 6. 예산 압박도 기준

예산 압박도는 예상 지출이 예산에 비해 얼마나 높은지를 나타내는 값입니다.

```text
예산 압박도 = 월말 예상 지출 ÷ 월 예산
```

예시:

```text
월말 예상 지출: 120,000원
월 예산: 100,000원
예산 압박도: 1.2
```

압박도가 높을수록 더 강한 소비 제한형 챌린지를 생성할 수 있습니다.

| 압박도           | 상태    | 의미           |
| ------------- | ----- | ------------ |
| 0.8 미만        | 안정    | 예산보다 여유 있음   |
| 0.8 이상 1.1 미만 | 주의    | 예산에 가까워지는 중  |
| 1.1 이상 1.5 미만 | 위험    | 예산 초과 가능성 높음 |
| 1.5 이상        | 초과 위험 | 강한 개입 필요     |

## 7. AI Engine 구조

AI 엔진은 `api/ai/moni_engine/` 아래에 위치합니다.

| 파일                 | 역할                                        |
| ------------------ | ----------------------------------------- |
| `preprocessing.py` | 거래 데이터를 일 단위 시계열로 변환하고 streak 등 분석용 특징 생성 |
| `prediction.py`    | Prophet/fallback 기반 카테고리별 지출 예측 및 예산 압박도 계산                       |
| `challenge.py`     | 예산 압박도에 따라 챌린지 유형, 난이도, 문구, XP 생성         |
| `engine.py`        | 백엔드에서 호출하는 AI 엔진 단일 진입점                   |

AI 엔진의 기본 흐름은 다음과 같습니다.

```text
Transactions + Category Budgets
→ preprocessing
→ prediction
→ budget pressure
→ challenge generation
→ Backend response
```

## 8. fallback 챌린지 흐름

초기 사용자이거나 소비 데이터가 부족하면 AI 엔진이 충분한 추천 결과를 만들기 어렵습니다.

이 경우 Moni는 기본 챌린지를 제공하는 fallback 흐름을 사용합니다.

```text
소비 데이터 부족
→ AI 결과 없음
→ fallback 챌린지 생성
→ 사용자는 초기 상태에서도 챌린지를 받을 수 있음
```

fallback은 미완성 상태가 아니라, 초기 사용자도 앱의 핵심 경험을 받을 수 있게 하는 안전 장치입니다.

## 10. 프론트엔드 구조

프론트엔드는 `frontend/mobile/`에 위치합니다.

| 경로            | 역할                          |
| ------------- | --------------------------- |
| `app/`        | Expo Router 기반 화면 라우트       |
| `app/(tabs)/` | 홈, 챌린지, 리포트, 소비, 마이페이지 탭 화면 |
| `app/auth/`   | 로그인 / 회원가입 화면               |
| `components/` | 공통 UI 컴포넌트                  |
| `services/`   | 백엔드 API 요청 함수               |
| `types/`      | API 응답 및 화면 데이터 타입          |
| `constants/`  | 색상, 타이포그래피, 기본 데이터          |
| `utils/`      | 예산 상태 계산, 카테고리 포맷 등 유틸 함수   |

프론트는 사용자에게 `mock`, `fallback`, `임시`, `테스트용` 같은 개발자용 문구가 노출되지 않도록 구성합니다.

## 14. 설계상 중요한 판단

### 1. 소비 예측은 행동 개입을 위한 수단이다

Moni의 핵심은 예측 자체가 아니라 예측 결과를 오늘의 행동으로 연결하는 것입니다.

```text
예측 결과
→ 예산 압박도
→ 오늘의 챌린지
→ 소비 행동 변화
```

### 2. 예산은 목표 기준이고, 지출 예측은 실제 행동 기준이다

예산을 수정해도 예상 지출이 바뀌지 않는 것은 정상입니다.
예상 지출은 실제 지출 속도 기반이고, 예산은 이 예상 지출이 위험한지 판단하는 기준입니다.

### 3. fallback은 초기 사용자 경험을 위한 안전 장치다

초기 사용자에게 소비 데이터가 충분하지 않아도 앱의 핵심 경험인 챌린지를 제공하기 위해 fallback 흐름을 둡니다.

### 4. 프론트는 실제 API 기준으로 구성한다

홈, 소비, 리포트, 챌린지, 마이페이지는 실제 API와 연결되어 있으며, 사용자가 입력한 데이터가 여러 화면에 반영되는 구조입니다.

## 15. 향후 확장 방향

* 실제 AI 추천 결과가 충분히 나오는 데이터 조건 고도화
* 리포트 내 AI 인사이트 문구 확장
* 챌린지 문구 다양화
* 캐릭터 성장 UI 고도화
* 주간 리포트 및 챌린지 달성률 분석
* 배포 환경 보안 설정 정리
* Swagger response model 정리
* GitHub Actions 기반 자동 타입 체크 / 백엔드 문법 체크 추가
