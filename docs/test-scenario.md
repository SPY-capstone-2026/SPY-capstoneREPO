# Moni Test Scenario

이 문서는 현재 Moni의 화면과 API를 함께 확인하기 위한 수동·통합 테스트 시나리오입니다.

```text
소비 기록·예산 설정 → 분석·챌린지 제안 → 완료 대기
→ 다음 날 검증 → XP·레벨업 보상 → 리포트·꾸미기·친구 확인
```

**기록 원칙:** 아래 체크박스는 미실행 상태입니다. 이번 문서 갱신은 정적 소스 확인만 수행했으며 실행 통과 결과를 대신하지 않습니다. `통과 / 실패 / 미실행 / API 계약 보완 대기`를 구분해 기록합니다.

---

## 1. 테스트 환경

### 프론트엔드

```powershell
cd C:\Users\espar\SPY-capstoneREPO\frontend\mobile
npx tsc --noEmit
npx expo start --web --clear
```

TypeScript 오류가 없을 때 웹을 실행합니다. 현재 확인 기준은 Expo Web입니다.

### 백엔드

```powershell
cd C:\Users\espar\SPY-capstoneREPO\api
python -m uvicorn main:app --reload
```

### 기본 주소

```text
Frontend: http://localhost:8081
Backend:  http://localhost:8000
Swagger:  http://localhost:8000/docs
```

실제 실행 포트·Origin·`EXPO_PUBLIC_API_BASE_URL`·현재 브랜치·커밋을 기록합니다. 배포를 검사하면 실제 서버 버전과 DB 스키마도 별도 확인합니다.

## 2. 시연용 계정

현재 `seed_all.py`에 정의된 개발 계정:

```text
email: student@moni.app
password: moni1234
```

해당 DB에 시드가 들어 있는 경우에만 사용할 수 있습니다. 계정 유무를 해결하기 위해 `seed_all.py`를 실행하지 않습니다. 이 파일은 기존 데이터를 삭제합니다. 친구 테스트에는 본인이 통제하는 별도 테스트 계정 2개를 준비합니다.

## 3. 사전 확인

### 확인 항목

```text
□ 현재 브랜치·커밋·실행 날짜·DB 구분을 기록했다.
□ 기존 데이터·환경 변수·로컬 변경사항을 보존했다.
□ 기존 DB에 nickname/memo/import_key 등 필요한 컬럼이 있다.
□ 서버 시작 로그에 예외가 없다.
□ docs 접속뿐 아니라 /me·거래 조회도 확인한다.
□ 프론트 Request URL과 Origin이 의도한 서버/포트이다.
□ TypeScript 검사 결과를 저장했다.
□ 운영 DB에서 시드·drop/create·미래 강제 정산을 하지 않는다.
```

백엔드 pytest는 기본 임시 SQLite를 사용합니다. `TEST_DATABASE_URL`을 지정하면 그 DB를 초기화하므로 운영·공유 데이터베이스를 절대 지정하지 않습니다. AI/LLM을 대역으로 처리하는 테스트와 실제 모델 실행을 구분합니다.

## 4. 인증 테스트

### 목표

회원가입·로그인·토큰 저장·내 정보 조회를 확인합니다.

### 절차

1. 별도 테스트 계정으로 가입합니다.
2. 동일 이메일 재가입과 잘못된 비밀번호를 확인합니다.
3. 로그인 성공 후 `/me` 조회와 홈 이동을 확인합니다.
4. 로그아웃 후 인증 API 접근을 확인합니다.

### 확인 항목

```text
□ 회원가입 응답은 user_id이며 토큰으로 오인하지 않는다.
□ 로그인은 JSON 요청이며 access_token을 저장한다.
□ 잘못된 비밀번호는 401로 구분한다.
□ 로그인 200 뒤 /me 실패를 별도로 식별한다.
□ 로그아웃 후 이전 사용자 정보가 새 계정에 남지 않는다.
□ 500과 CORS 문구가 함께 나오면 서버 Traceback·스키마를 확인한다.
```

## 5. 마이페이지 테스트

### 목표

프로필·닉네임·성장 상태·설정 저장을 확인합니다.

### 절차

닉네임, 이메일, 수입 유형, 수입일, 소비 성향을 수정하고 재조회합니다. 알림 토글과 로그아웃도 확인합니다.

### 확인 항목

```text
□ 닉네임 변경은 내 정보 수정에서 수행한다.
□ 길이·허용 문자·중복 닉네임 오류를 표시한다.
□ 재조회 후 수정한 값이 유지된다.
□ XP·현재 레벨·포인트가 /me와 일치한다.
□ 알림 선호 저장과 실제 푸시 발송을 혼동하지 않는다.
□ PreferenceRow 등에서 테마 훅을 선언한 범위가 올바르다.
```

회원가입에 닉네임 입력이 없는 것은 현재 UI 명세입니다. 서버의 선택적 닉네임 지원과 구분합니다.

## 6. 소비 기록 테스트

### 목표

지출 CRUD·분류·메모·웹 삭제를 확인합니다.

### 절차

1. 날짜·거래처·금액·카테고리·메모를 입력해 등록합니다.
2. 카테고리를 비워 추천 가능한 거래처와 추천 불가 거래처를 각각 등록합니다.
3. 존재하지 않는 카테고리를 테스트 API로 보내 400을 확인합니다.
4. 날짜·금액·메모를 수정하고 `memo:""`로 삭제합니다.
5. 삭제 확인창에서 취소와 확인을 각각 실행합니다.

### 확인 항목

```text
□ 저장 결과가 목록에 표시된다.
□ 자동 분류 실패를 성공 또는 빈 카테고리 저장으로 처리하지 않는다.
□ 없는 사용자 카테고리는 400으로 안내한다.
□ 메모 생략/null은 유지, 빈 문자열은 삭제한다.
□ Web 삭제 확인과 처리 중 중복 클릭 방지가 동작한다.
□ 삭제 후 거래 목록과 재조회한 통계가 갱신된다.
□ 이미 확정된 챌린지가 거래 수정으로 자동 재검증된다고 가정하지 않는다.
```

## 7. 날짜 기준 테스트

### 목표

### 절차

이번 달과 지난달에 테스트 거래를 만들고, 거래 날짜를 다른 월로 옮겨 두 기간을 다시 조회합니다.

### 확인 항목

```text
□ 직접 날짜를 선택할 수 있다.
□ 잘못된 달력 날짜를 거부한다.
□ 소비 화면은 해당 월의 실제 지출로 예산 사용률을 계산한다.
□ 날짜 수정 후 이전/새 기간 리포트가 함께 갱신된다.
□ 리포트의 서버 date.today와 챌린지 KST 기준 차이를 경계 시각에 점검한다.
□ 파일 미리보기의 occurred_at을 날짜/시간 표시로 정확히 변환한다.
```

## 8. 예산 테스트

### 목표

예산 수정·변경 이력·챌린지 대상·재생성 예약을 확인합니다.

### 절차

카테고리 예산을 증액·감액하고 알림 기준 및 챌린지 대상 여부를 변경합니다. 변경 이력과 오늘의 목표를 다시 조회합니다.

### 확인 항목

```text
□ 월 예산 0 이상, 서버 알림 기준 1~100%를 확인한다.
□ 80은 80%이며 0.8과 혼동하지 않는다.
□ 변경 이력에 이전/새 예산·방향·시각이 남는다.
□ 예산 증가 + 챌린지 대상일 때 재생성 예약 여부를 확인한다.
□ VERIFYING/SUCCESS/FAILED 목표는 PENDING 재생성 대상이 아니다.
□ 예산 변경 자체가 거래 기반 예측을 바꾼다고 설명하지 않는다.
□ 독립 예산 탭 없이 소비 화면에서 설정한다.
```

현재 UI는 알림 기준 0도 허용하지만 서버는 1 이상이므로 불일치 항목으로 기록합니다.

주간·월간 통계, 기간 이동, 캐시, 총평을 확인합니다.

### 절차

진행 중인 기간·종료된 기간·빈 데이터 기간을 조회하고, 해당 거래를 바꾼 뒤 다시 조회합니다.

### 확인 항목

```text
□ 주간 합계·지난주 비교·일별 추이·카테고리 비교가 일치한다.
□ 월간 예산·지출·주차별 집계·초과 항목을 확인한다.

□ LLM 키 없음/실패 시 대체 총평을 확인한다.
```

## 11. 챌린지 테스트

### 목표

생성·완료 대기·취소·최종 확정·보상 중복 방지를 확인합니다.

### 절차

1. 오늘의 목록 조회 → 필요 시 생성합니다.
2. 한도·난이도·XP와 메타데이터를 확인합니다.
3. 완료 표시 후 VERIFYING과 XP/포인트 변화 없음을 확인합니다.
4. 당일 표시를 취소합니다.
5. 테스트 DB의 과거 VERIFYING 목표로 성공/실패 검증을 확인합니다.
6. 같은 정산을 다시 실행하여 중복 지급이 없는지 확인합니다.

### 확인 항목

```text
□ 같은 날짜 생성 재요청이 중복 목표를 만들지 않는다.
□ SUCCESS 요청이 즉시 SUCCESS가 아니라 VERIFYING으로 반환된다.
□ 완료 표시/취소 시 XP·포인트가 변하지 않는다.
□ 한도 있는 목표는 해당 날짜·카테고리의 등록 지출로 판단한다.
□ 성공 시 XP, 레벨업 시 포인트·지정 아이템이 반영된다.
□ 확정 항목 수정 제한과 중복 정산 멱등성을 확인한다.
□ 한도 없는 fallback의 승인 정책을 별도로 기록한다.
□ Actions 예약 00:05와 조회 보정의 날짜 기준을 구분한다.
□ /challenges/history의 MISSED와 DB PENDING을 구분한다.
```

정산 팝업은 현재 잘못된 경로를 호출하므로 팝업 표시 테스트는 계약 보완 전까지 실패/보류로 기록합니다. 운영 DB에 미래 `as_of`를 보내 보상을 당겨 지급하는 시연은 하지 않습니다.

## 12. AI / fallback 테스트

### 목표

실제 ARIMA 실행과 각 대체 경로를 구분합니다.

### 확인 항목

```text
□ 90개 이상 관측·빈도 또는 거래 50건·잔여일수 조건에서 ARIMA 호출을 확인한다.
□ 내부 40개 관측 방어와 외부 90개 진입 기준을 혼동하지 않는다.
□ ARIMA(7,0,1) 실패 시 (1,0,0) 재시도를 확인한다.
□ 재실패·비정상 예측·가드 초과 시 평균 대체를 확인한다.
□ 빈 데이터는 no_data 또는 서버 기본 목표로 처리한다.
□ LLM 미설정/실패는 규칙 문구로 처리한다.
□ model_used만으로 내부 평균 대체 여부를 단정하지 않는다.
□ API pytest의 AI 대역과 실제 모델 실험을 구분한다.
```

모델 정확도 평가는 별도의 시계열 분할·실제값 대조가 필요합니다. 기존 비교 리포트 표를 최신 ARIMA 재측정 결과로 인용하지 않습니다.

## 14. 최종 통합 시나리오

```text
로그인 → 내 정보·닉네임 확인
→ 소비 기록 추가·메모·과거 날짜 수정
→ 항목별 예산 설정·변경 이력
→ 주간/월간 리포트
→ 오늘의 챌린지·완료 대기·취소
→ 테스트 DB의 과거 챌린지 검증·보상·이력
→ 상점·인벤토리·장착·테마
→ 친구 요청·프로필·방 확인
→ 파일 미리보기·등록·재업로드 (계약 보완 후)
→ 로그아웃·재로그인·계정 전환 확인
```

| 대상 | 현재 문서상 상태 |
|---|---|
| 소비/예산/일반 화면 | 실행 검증 필요 |
| ARIMA 실제 추론 | 경계·실패 경로와 수치 실험 별도 필요 |
| 정산 서버 | 테스트 DB에서 시각·성공/실패·중복 지급 확인 필요 |
| 정산 팝업 | API 계약 보완 필요 |
| CSV/XLSX 등록 | 프론트 필드·제외·제한·토스트 매핑 보완 필요 |
| 친구 랭킹 UI | 서버 API만 확인; 화면 연결 별도 |

## 16. CSV / XLSX 추가 시나리오

### 목표

파일 입력부터 실제 저장 결과까지 확인합니다. 현재 프론트 계약을 먼저 수정해야 하는 항목은 보류로 기록합니다.

| 케이스 | 확인할 결과 |
|---|---|
| 정상 토스 XLSX | TOSS 형식, 날짜·거래처·금액·추천 분류 |
| 직접 만든 CSV | GENERIC 형식, 헤더/인코딩·시간 기본값 |
| 수입·환불·혜택 회수 | 제외 이유와 대응 결제 취소 후보 |
| 이체 | 가져오기 가능 여부와 기본 비선택 |
| 읽지 못한 행 | INVALID 이유, 다른 정상 행은 확인 가능 |
| 추천 없는 선택 행 | 분류 선택 전 등록 금지 |
| 동일 파일 재업로드 | 기존 거래가 중복 저장되지 않음 |
| 동시에 등록 | 중복 제약과 409 안내, 데이터 일관성 |
| XLS/5 MiB 초과 | 서버 지원 범위와 맞는 선택/오류 안내 |
| 확정 결과 | inserted/skipped_duplicate/cancelled 매핑, 목록 재조회 |

`source_format`, `occurred_at`, `import_key`가 손실되지 않는지 확인하고, 기존 결제 취소는 `cancel_tx_ids`와 소유자 검사를 포함해 점검합니다.
